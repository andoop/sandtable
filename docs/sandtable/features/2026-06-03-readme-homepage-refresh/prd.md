# README GitHub 首页重塑 · PRD

> 我在用 writing-prd 把需求固化为 PRD。
> 对应 project.md 北极星（让 AI 把简单需求做成逻辑闭环、细节完美的功能）/ 继承 constraints.md 红线。实现细节见 plan.md，具体场景见 tests.md。

## 1. 目标
把仓库 `README.md` 重塑成一个成熟、形象、简洁、AI 友好的 GitHub 首页：让第一次进入仓库的人能在很短时间内看懂 Sandtable 的方法论精髓、和 `superpowers` 的差异、为什么值得尝试，以及这个仓库正在用 Sandtable 自己迭代自己。

## 2. 背景与现状（已确认事实，标来源）
- 当前 README 已经说明 Sandtable 是“沙盘推演驱动开发”方法论插件，也提到借鉴了 Karpathy 四原则与 `superpowers` 的子 agent 编排思想，但首页前半段仍偏“定义说明”，还没有把“为什么现在就该试”压缩成更强的首屏叙事（`README.md:1-27`）。
- 当前 README 有“核心特性”“命令表”“目录结构”，但没有一个面向 GitHub 首页访客的强视觉流程图，也没有一个显式的对比块来帮助读者快速理解 Sandtable 与 `superpowers` 的重心差异（`README.md:9-27`、`README.md:54-123`）。
- 项目北极星明确写着：Sandtable 既是方法论本体，也用自身方法论自举改进自己；这说明 README 可以合理突出“我们自己也在用这种方式迭代这个仓库”的事实（`docs/sandtable/project.md:5-11`）。
- 仓库当前已经具备 `/sandtable-autopilot`、`autonomous-orchestration`、`state-and-memory`、`docs/sandtable/` 等能力，这些都可以作为首页差异化卖点，而不是停留在抽象口号（`README.md:13-20`、`skills/autonomous-orchestration/SKILL.md:13-19`、`skills/state-and-memory/SKILL.md:6-18`）。
- `superpowers` README 可核实地强调了 brainstorming、writing-plans、subagent-driven-development、test-driven-development、code review、git worktrees 等流程能力；这意味着 Sandtable 的对比表述必须建立在“重心差异”上，而不是虚构对方没有的方法论能力（来源：`https://raw.githubusercontent.com/obra/superpowers/main/README.md`，已核读）。

## 3. 方案探索
- **方案 A：只在现有 README 上追加几段卖点。**
  - 优点：改动少。
  - 缺点：首页结构不会本质改善，访客仍需要顺着长文自己提炼价值。
- **方案 B：重构 README 首屏叙事与信息层级。**
  - 优点：可以把“一句话价值主张 → 为什么不同 → 流程图 → 对比 → 自举证据 → 快速开始”压成更成熟的首页路径。
  - 缺点：需要重写大部分 README 的组织方式。
- **方案 C：做成强营销文案风格。**
  - 优点：更有冲击力。
  - 缺点：容易失真，且不够 AI 友好，和项目“实事求是”的基调冲突。

**推荐：方案 B。** 既能显著提升 GitHub 首页形象，又能保持方法论仓库应有的事实密度与可扫描性。

## 4. 用户故事 / 场景
- 作为第一次来到仓库的开发者，我希望 30 秒内看懂 Sandtable 是什么、解决什么问题、为什么和常见“让 AI 直接写代码”的做法不同。
- 作为已经了解 `superpowers` 的用户，我希望 README 能快速告诉我 Sandtable 不是在重复同一套叙事，而是把“推演、对抗、状态机、异常回修正”做得更重、更显式。
- 作为准备试用的 AI/开发者，我希望首页直接给出清晰流程、差异化卖点与快速开始入口，而不是翻很久才能知道怎么上手。

## 5. 功能需求
- **FR1（首屏价值主张）**：README 开头必须用更成熟、更简洁的首页表达方式，在首屏明确回答“Sandtable 是什么”“为谁而做”“解决什么问题”；首屏主句必须说明它要避免什么失控或走偏、换来什么结果，并让读者快速感知这是一个给 coding agent 的完整方法论插件，而不是零散 prompt 集。〔已确认：来源于开发者原话“成熟、形象、简洁、AI 友好、让人一下子就知道” + mental 预演已指出“解决什么失败/痛点”尚未前置〕
- **FR2（流程图明确）**：README 必须包含一个在 GitHub 上可直接阅读的明确流程图，清楚表达 Sandtable 的闭环：从需求进入，到侦察、目标、测试、计划、三类推演，再到集成验证；同时要看得出“发现异常就回修正循环”。该流程图必须在首个滚屏内或紧接首屏下方出现，不能继续下沉到后文。流程图本身或紧邻其后的说明还必须提供一层白话解释，让第一次来的访客不依赖 `RECON / OBJECTIVES / MENTAL / REDTEAM / IMPL` 这些术语也能看懂“先摸清、再定目标、再计划、再预演、出问题就回修正”的闭环。〔已确认：开发者明确要求“流程图明确” + mental 预演已指出流程图位置约束不足〕
- **FR3（和 superpowers 的对比）**：README 必须加入一个事实受约束的对比区块，帮助读者快速理解 Sandtable 与 `superpowers` 的侧重点差异；对比文案只允许写“已核实事实 + 重心差异 + 可见的首页呈现差异”，不得虚构 `superpowers` 没有的能力，也不得写任何未附事实锚点的 superiority claim，例如“更强 / 更完整 / 更可靠 / 更适合 / 更系统”之类的结论。**每一个对比点**都必须严格遵守两句制模板：`(1)` 第一句只写一个可直接回指到已核读 `superpowers` README 的事实；`(2)` 第二句只写与该事实对应的 Sandtable 仓库内可指认事实。不允许出现第三句、点评句、评价形容词、替读者下判断的语气、或脱离仓库事实的体验推断。两句都必须在最终 README 中**内联显式呈现一个具体名词锚点**，不接受宽泛总括句，也不允许一句里并列多个锚点。README 中凡提及 `superpowers` 的比较句，只允许出现在两处：`(a)` 前两屏内那 1 条极短事实型微对比；`(b)` 正式的 `Sandtable vs Superpowers` 对比区块。`Why`、标题下副文、首屏主句、自举证明、Quickstart、命令入口等其它 section 不得额外引入新的 `superpowers` 比较句。〔已确认：开发者明确要求“有对 superpower 对比，突出我们优势” + 已核读 superpowers README + mental/redteam 已指出作用域绕开风险〕
- **FR4（突出 Sandtable 精髓）**：README 必须把本仓最核心、最能形成记忆点的能力前置出来，至少包括“三类推演”“异常即停并回写计划”“持久状态与记忆”“推演驱动的自我完善”“自举迭代”。对于已经知道 `superpowers` 的访客，前两屏还必须出现 1 条极短、基于已核实事实的微对比信号，用来说明 Sandtable 不是同题复述；这条微对比只允许点出一个事实差异，不展开完整对比表。〔已确认：来自当前项目北极星、README 现有事实与开发者原话 + 开发者新增反馈“首页不应过度强调 /sandtable-autopilot，而应更突出推演与自我完善”〕
- **FR5（自举证明）**：README 必须明确说明这个仓库正在使用 Sandtable 自己迭代自己，让访客感受到这不是一套只写给别人的方法论。必要时可引用 `docs/sandtable/` 的存在作为证据。〔已确认：开发者原话“我们自己也在通过这种方式迭代” + `project.md` 明确自举〕
- **FR6（保留上手路径）**：在重塑首页叙事后，README 仍必须保留清晰可用的安装/接入与命令入口，不得为了首页包装而牺牲试用路径；**首屏必须出现一条可行动的“立刻试用”摘要**，至少说明把哪句话发给 AI、去哪里安装/接入、先执行哪一步；前两屏内必须同时有可单跳到同一个 `Quickstart` 区块的锚点，让被说服的访客无需继续翻很久就知道下一步。README 的默认推荐试用路径应统一为：**把一句安装指令发给自己的 AI，让它阅读 `INSTALL.md` 并把 Sandtable 安装进当前项目**，避免再按 `Claude Code` / `Cursor` 拆成多条首页选择题。首屏试用锚点必须落到同一个 `Quickstart` 区块，不能再跳向其它“安装/接入”型 section；该区块应保留统一的 AI 快速接入三件套：`1` 句可复制的安装指令、`1` 个安装后的接线动作说明、以及安装后的第 `1` 条命令。若不同 harness 在最后接线动作上有差异，README 只需明确“按 AI 的安装结果完成最后接线；若提示重载窗口/重开工作区使规则生效，就照做”，具体分支留在 `INSTALL.md`。〔已确认：`INSTALL.md` 已存在可跨 harness 复用的 AI 安装指令；开发者进一步确认 README 无需保留 `Claude Code marketplace` 与 `Cursor` 分栏〕
- **FR7（AI 友好与 GitHub 友好）**：README 必须保持结构可扫描、段落短、标题清晰、信息分块稳定，便于人类快速浏览，也便于 AI 读取与引用；应避免大段空泛宣传语。首页重构必须受长度预算约束：新增首页模块时要同步压缩、合并或删除旧说明，不能在现有 README 上无限叠加。预算写成硬门槛：首屏只允许“标题 + 1 句副文 + `<=5` 条核心记忆点 + 1 条试用入口摘要”，闭环图紧随其后；前两屏不得展开对比表和完整 Quickstart；README 总行数不得明显高于当前版本，上限定为 **160 行**。首屏每条记忆点只允许“1 个能力 + 1 个结果”，不得并列多个方法论名词；其中至少 2 条必须是结果导向句，而不是能力名词句；并且每条“结果”都必须能回指到 README 内紧邻可见的流程、目录、命令或仓库事实，不能写成脱离仓库事实的通用收益口号。标题下副文、首屏主句、`Why Sandtable / Why not just let AI code` 段里的每一句，也都只能陈述仓库内可见机制及其可观察结果；禁用“更/最/真正/不再/保证/更值得试”等词，并要求每句都能就近落到紧邻可见的流程、命令、目录或文档事实。〔已确认：开发者明确要求“AI 友好” + mental 预演已指出长度约束不足〕

## 6. 验收标准（成功定义 · 抽象层；具体场景见 tests.md）
- [ ] 仓库首页在前两屏内就能讲清 Sandtable 的一句话价值、核心流程和差异化优势，而不是需要读完整篇 README 才能理解。
- [ ] 首页前两屏只优先解决两个判断题：“它为什么值得试”以及“它怎样通过异常回修正形成闭环”；其他信息不得挤占这两个问题的表达优先级。
- [ ] 首页存在清晰的流程图，并能让读者一眼看出“异常会回到修正循环”这一方法论核心。
- [ ] 首页流程图不仅存在，而且第一次来的访客不依赖仓内术语也能看懂其白话含义。
- [ ] 首页存在一个事实约束下的 `superpowers` 对比区块，既能突出 Sandtable 的重点，也不靠失实贬低对方来取胜；其中不出现无证据的优越性判断词，且每个对比点的两句都各自显式含有一个具体名词锚点。
- [ ] README 中凡出现 `superpowers` 的比较句，都只能是“前两屏 1 条极短微对比”或正式 `Sandtable vs Superpowers` 对比区块中的逐点两句制；其它 section 不得额外夹带比较句。
- [ ] 对已经知道 `superpowers` 的访客，前两屏内就能获得至少 1 条极短、事实型的差异信号，而不是只能靠后文完整对比表确认差异。
- [ ] 首页明确传达“这个仓库正在用 Sandtable 自己迭代自己”的信号。
- [ ] 首页改造后仍保留可直接执行的安装/接入和命令入口，并且从 README 顶部往下读，首屏就能看到一条可行动的试用入口摘要，前两屏内能看到明确的试用锚点。
- [ ] 首页改造后仍保留默认推荐试用路径，读者不需要先在多条安装方式里自行做选择；`Quickstart` 在同一落点内即可完成“把安装指令发给 AI -> 完成最后接线 -> 执行第一条命令”的最短启动。
- [ ] 若安装完成后存在“重载窗口/重开工作区，使规则生效”这类接线动作，README 的 `Quickstart` 必须明确提示“按 AI 的安装结果完成最后接线”，而不是假定读者会自己去 `INSTALL.md` 深处推断。
- [ ] 首页改造没有靠简单叠加内容完成，而是通过压缩和重组把信息密度维持在可扫描范围内；不会把 README 变成长而空的宣传页，且总行数不超过 160 行。

## 7. MUST（绝对要做）
- 必须把“成熟、形象、简洁、AI 友好”落实为信息架构改造，而不是只换几句文案。
- 必须有清晰流程图。
- 必须有 `superpowers` 对比，并且基于已核实事实。
- `superpowers` 对比中的每个对比点都必须带已核实事实锚点，且只能落在“重心差异”或“读者先感知到什么”这两类合法内容里。
- `superpowers` 对比中的每个对比点都必须严格是两句制：第一句写 `superpowers` 已核实事实，第二句写 Sandtable 仓库事实；出现第三句或点评句即不合格。
- `superpowers` 对比中的每句都必须显式带一个具体名词锚点，不接受宽泛总括句。
- README 中凡涉及 `superpowers` 的比较句，都只能落在“前两屏 1 条极短微对比”或正式对比区块；其它 section 不得借 `Why` / 自举 / Quickstart 之名追加比较句。
- 必须把“三类推演 + 异常回修正 + 持久状态 + 推演驱动的自我完善 + 自举迭代”这些 Sandtable 精髓前置。
- 前两屏必须包含 1 条极短、事实型的 `superpowers` 微对比信号，但不得在前两屏展开完整对比表。
- 必须保留快速开始与命令入口，让首页既能说服人也能让人立刻试。
- 必须让“立刻试用”的摘要出现在首屏，且前两屏内单跳可达，而不是只在后文完整展开。
- 必须给出统一的默认推荐试用路径：把安装指令发给 AI，让它阅读 `INSTALL.md` 并完成接入。
- `Quickstart` 必须是唯一试用落点；前两屏短锚点只能跳到 `Quickstart`，不能再跳向其它“安装 / 接入”类 section。
- `Quickstart` 必须给出 1 句可复制的安装指令、1 个安装后的接线动作说明、以及安装后的第 1 条命令。
- 必须控制首页篇幅，新增版块要伴随删改旧说明，不能只做加法。
- 必须把前两屏的表达优先级固定为：痛点/结果导向的价值主张 → 3-5 个核心记忆点 → 紧随其后的闭环图；`superpowers` 对比、自举证明与完整 Quickstart 展开应下沉到后续 section，只允许在前两屏留下短锚点。
- 闭环图必须配白话解释，不得只给术语节点让首次访客自行翻译。
- 必须把 README 总行数控制在 160 行以内。
- 首屏每条记忆点都必须是“1 个能力 + 1 个结果”；至少 2 条是结果导向句。
- 首屏每条记忆点里的“结果”都必须能回指到 README 内紧邻可见的仓库事实；凡删去能力半句后仍像通用广告语的结果句，一律不合格。
- 标题下副文、首屏主句、`Why` 段每一句都必须能就近回指到仓库事实；凡删去锚点后仍像口号句的表达，一律不合格。

## 8. MUST NOT（绝对不能做）
- 不得写没有依据的性能、成功率、质量提升百分比。
- 不得把 `superpowers` 描述成“没有规划/没有子 agent/没有工作流”等与已核读内容冲突的话。
- 不得把 README 改成大段营销口号，牺牲事实密度和可操作性。
- 不得为首页视觉效果引入仓库里不存在的新功能、新命令或新能力。
- 不得顺手修改与本需求无关的命令、skill 或脚本。
- 不得把安装/接入/命令入口埋到长文后半段，造成“被说服但不能立刻试”的首页断层。
- 不得在对比区块中写任何没有事实锚点支撑的优越性判断词。
- 不得在正式对比区块与前两屏微对比之外，额外写新的 `superpowers` 比较句。
- 不得在首屏只留下一个空泛跳转词或弱锚点，而不给出最短试用下一步。
- 不得在 README 首页继续保留与仓库现状不符的 `Claude Code marketplace` 安装说法。
- 不得把安装完成后真正生效所需的最后接线动作完全藏在 `INSTALL.md` 或后文，让 README 只给半套三件套。
- 不得使用无锚点优越词、替读者下判断的煽动句、或只报抽象概念不报仓库事实的口号句。
- 不得在对比区块两句制之外追加第三句点评或解释性结论。

## 9. 非目标 / 暂不做（YAGNI）
- 不做独立官网或图片素材体系。
- 不做 README 之外的大规模品牌物料改造。
- 不新增演示视频、GIF、徽章体系或第三方埋点。
- 不修改方法论本体，只重塑对外首页表达。
